# Rollback/recovery runbook — BS-148 нік і місто користувача

Стосується міграції `20261026090000_profile_handle_city` (підетап A
[плану BS-148](../plan/bs-148-profile-design.md)):

- функція `generate_user_handle()` — `user` + 8 випадкових цифр;
- `User.city TEXT NULL`;
- `User.handle TEXT NOT NULL DEFAULT generate_user_handle()`, індекс `User_handle_key` (UNIQUE),
  CHECK `user_handle_format` (3–30 символів, `^[a-z0-9]+([-_][a-z0-9]+)*$`);
- backfill: кожен наявний користувач отримує унікальний згенерований нік.

Золоте правило [catalog-correction-migration-rollback.md](./catalog-correction-migration-rollback.md)
діє й тут: застосований `migration.sql` не редагується, `prisma migrate reset` не є способом
«скасувати». Відкат схеми — лише відновлення з backup (поки користувачі нічого не змінили) або **нова
forward-міграція**.

## 1. Сумісність версій

| Пара                          | Працює? | Чому                                                                                                                                                                                                 |
| ----------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Нова схема + старий API (R0)  | Так     | R0 створює користувачів без ніка — нік видає `DEFAULT` бази. Нових колонок R0 не читає й не пише.                                                                                                    |
| Нова схема + новий API        | Так     | Цільовий стан.                                                                                                                                                                                       |
| Новий API + старий web        | Так     | Старий web парсить `Me`/`PublicUser` zod-схемами без `handle`/`city`; zod за замовчуванням відкидає зайві поля.                                                                                       |
| Старий API + новий web        | **Ні**  | Новий `meSchema`/`publicUserSchema` вимагає `handle`: сесія й списки людей не пройдуть парсинг. Web розгортається **після** API.                                                                       |
| Стара схема + новий API       | **Ні**  | Prisma Client нового API вибирає `handle`/`city`, яких немає. Міграція застосовується **до** розгортання API.                                                                                         |

Звідси єдиний порядок: **backup → міграція → API → web.** Вікна, де вставка падає, немає: стара збірка
API між міграцією й власним оновленням отримує нік від бази. Саме тому тут одна міграція, а не
expand/contract (див. «Відхилення» в розділі A плану).

## 2. Перед розгортанням

1. **Backup.** `pg_dump -Fc`, файл поза сервером БД. Без перевіреного backup не починати.
2. Знімок: `SELECT count(*) FROM "User";` — після міграції кількість має збігтися.
3. Тривалість backfill. Цикл перевіряє вільність кожного кандидата запитом до `"User"` ще **до** появи
   унікального індексу, тобто послідовним скануванням: O(n²) за кількістю користувачів. Для десятків
   і сотень людей (масштаб BookSwap) це частки секунди. Якщо користувачів раптом десятки тисяч —
   спершу виміряти час на копії бази, а не на проді.

## 3. Перевірки після міграції (інваріанти)

```sql
-- 1. Кількість користувачів не змінилася (порівняти зі знімком §2.2).
SELECT count(*) FROM "User";

-- 2. Жодного порожнього чи невалідного ніка (CHECK це гарантує; запит — контроль, що CHECK на місці).
SELECT count(*) FROM "User"
WHERE handle IS NULL OR handle !~ '^[a-z0-9]+([-_][a-z0-9]+)*$' OR char_length(handle) NOT BETWEEN 3 AND 30;
-- очікується 0

-- 3. Обмеження й DEFAULT на місці.
SELECT conname FROM pg_constraint WHERE conname = 'user_handle_format';
SELECT indexname FROM pg_indexes WHERE indexname = 'User_handle_key';
SELECT column_default FROM information_schema.columns WHERE table_name = 'User' AND column_name = 'handle';
-- очікується generate_user_handle()
```

Smoke після API: `GET /api/v1/auth/session` повертає `user.handle` формату `user` + 8 цифр і
`user.city: null`; реєстрація нового користувача видає такий самий нік.

## 4. Відкат

| Ситуація                                                     | Дія                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Збій міграції або перевірок §3, API ще не оновлено           | Лишити R0 (він працює з будь-яким станом цієї міграції, §1). Розібратися з причиною; якщо міграцію позначено як FAILED — відновити БД з backup §2.1 і повторити.                                                                                                                                                                        |
| Проблема в новому API або web                                | **Відкотити код, не схему.** Спершу web, потім API до R0 (порядок, зворотний до §1). Схема лишається: R0 з нею сумісний, нікнейми й міста користувачів зберігаються до наступного розгортання.                                                                                                                                          |
| Справді треба прибрати колонки (рішення PO, не реакція на збій) | Лише нова forward-міграція: `DROP CONSTRAINT "user_handle_format"`, `DROP INDEX "User_handle_key"`, `DROP COLUMN "handle"`, `DROP COLUMN "city"`, `DROP FUNCTION generate_user_handle()`. **Втрачає змінені користувачами ніки й міста** — перед нею окремий `pg_dump`. Після підетапу B (`/u/<нік>`) це ще й ламає адреси людей — без рішення PO не робити. |

Відновлення з backup після того, як користувачі вже змінювали нік чи місто, втрачає ці зміни (і все
інше, записане після backup) — такий шлях лише за явним рішенням PO.

## 5. Автоматизований доказ

`apps/api/test/db/profile-handle-migration.db-spec.ts` накочує міграції до цієї на окрему guarded
scratch-БД (`test/db/migration-scratch.ts`), наповнює її користувачами в схемі R0, застосовує цю
міграцію й перевіряє:

- кожен наявний користувач отримав унікальний нік `user` + 8 цифр;
- решта колонок не змінилася, `city` — `NULL`;
- вставка у стилі R0 (без ніка) отримує нік від бази;
- CHECK відхиляє нік поза форматом, приймає `danylo-ohurtsov_2`;
- унікальний індекс не дає двом людям один нік.

Тест — частина `pnpm test:db` / `./gate.sh`. Відповідність `schema.prisma` міграціям перевірено
`prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` на
scratch-базі після `migrate deploy` — розбіжностей немає.
