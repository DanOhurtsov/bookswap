# Runbook — фото профілю в Cloudflare R2 (BS-148)

Фото профілю завантажується через `POST /api/v1/me/avatar`. API перекодовує його в квадрат 512×512 WebP без
метаданих і кладе в бакет R2. Браузер завантажує фото **напряму з публічного домену бакета**, а не через API.
Реалізація лежить в `apps/api/src/users/avatar/`, правила — у [плані BS-148, розділ C](../plan/bs-148-profile-design.md).

## 1. Режими сховища

| `AVATAR_STORAGE` | Де фото                     | Хто їх роздає                                  | Де дозволено                       |
| ---------------- | --------------------------- | ---------------------------------------------- | ---------------------------------- |
| `memory`         | у пам'яті процесу API       | сам API: `GET /api/v1/avatars/<власник>/<файл>` | dev і тести; **production — ні**   |
| `r2`             | бакет R2                    | публічний домен бакета                          | будь-де; **production — лише так** |

Зі значенням `memory` у production API не стартує: це перевіряє `env.validation.ts`. У режимі `memory`:

- фото зникають із кожним рестартом API, і на їхньому місці показуються ініціали;
- адреса фото має вигляд `http://localhost:<PORT>/api/v1/avatars/…`, тобто розрахована на локальний web.

## 2. Налаштування R2 (один раз на середовище)

1. **Бакет.** Cloudflare → R2 → створити бакет, наприклад `bookswap-avatars`, окремий для кожного середовища.
   Зберігати в ньому щось інше не можна: ключі API мають доступ до всього бакета.
2. **Публічний доступ.** У налаштуваннях бакета підключити **власний домен**, наприклад `avatars.<домен>`.
   Адреса `r2.dev` годиться лише для перевірки: Cloudflare обмежує її швидкість і не радить для production.
   Адреса домену без `/` у кінці стає значенням `R2_PUBLIC_BASE_URL`.
3. **API-токен.** R2 → Manage API tokens → новий токен з правами **Object Read & Write** лише на цей бакет.
   Не Admin і не доступ до всіх бакетів: токен лежить в оточенні API, а витік ширшого токена відкрив би решту
   акаунта. Access Key ID і Secret Access Key стають `R2_ACCESS_KEY_ID` і `R2_SECRET_ACCESS_KEY`.
4. **Account ID** (видно на сторінці R2) стає `R2_ACCOUNT_ID`. Endpoint API збирає сам:
   `https://<account>.r2.cloudflarestorage.com`.
5. **Оточення API:**
   ```
   AVATAR_STORAGE=r2
   R2_ACCOUNT_ID=…
   R2_ACCESS_KEY_ID=…
   R2_SECRET_ACCESS_KEY=…
   R2_AVATAR_BUCKET=bookswap-avatars
   R2_PUBLIC_BASE_URL=https://avatars.<домен>
   ```
   Усі п'ять змінних обов'язкові: без будь-якої з них API не стартує.
6. **CORS на бакеті не потрібен.** Фото показуються тегом `<img>`, а не через `fetch`.

## 3. Перевірка після налаштування

1. У лозі старту API є рядок `Сховище фото профілю: r2`.
2. Завантаження фото в профілі (або `POST /api/v1/me/avatar` із сесією) повертає 200, а `avatarUrl` починається
   з `R2_PUBLIC_BASE_URL`.
3. Адреса з `avatarUrl` відкривається в браузері без сесії. Відповідь має тип `image/webp` і
   `Cache-Control: public, max-age=31536000, immutable`.
4. Після другого завантаження першого об'єкта в бакеті вже немає.

## 4. Ротація ключів

1. Створити **новий** токен з тими самими правами (§2.3), старий поки не чіпати.
2. Записати нові `R2_ACCESS_KEY_ID` і `R2_SECRET_ACCESS_KEY` в оточення й перезапустити всі інстанси API.
3. Перевірити завантаження (§3.2).
4. Відкликати **старий** токен.

Під час ротації фото не зникають: вони в бакеті, а не в ключах. Браузери завантажують їх із публічного домену,
який ключів не потребує.

## 5. Що може піти не так

| Симптом                                        | Причина й дія                                                                                                                                                                                                                                     |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API не стартує, помилка про `AVATAR_STORAGE`   | `memory` у production або неповний набір `R2_*`. Задати всі змінні з §2.5.                                                                                                                                                                         |
| `POST /me/avatar` → 500                        | R2 недоступний або ключ відкликано. Профіль при цьому **не змінюється**: адреса записується лише після успішного збереження файла. Перевірити токен (§4).                                                                                       |
| Фото не відкривається за адресою               | Публічний доступ бакета вимкнено або домен не підключено (§2.2).                                                                                                                                                                                   |
| У лозі `Не вдалося видалити фото avatars/…`    | Старий файл після заміни чи видалення не видалився. Профіль від цього не страждає (видалення best-effort), лишається «сирота» на кілька десятків КБ. Ключ із лога достатньо видалити з бакета вручну.                                          |

**Сироти.** Видалення старого фото — best-effort. Сирота лишається, коли збій стався між записом нової адреси й
видаленням старого файла, або коли та сама людина завантажила два фото одночасно. Щоб знайти сирот, порівняйте
об'єкти під префіксом `avatars/<userId>/` з `User.avatarUrl`: усе, на що профіль не посилається, можна видалити.
Автоматичного прибирання немає: за масштабу BookSwap воно не окупається.

## 6. Дані, збережені до BS-148

Раніше `avatarUrl` задавався вручну через `PATCH /me`. Такі зовнішні адреси лишаються в базі й показуються далі.
Нову адресу можна встановити лише завантаженням. Під час заміни чи видалення фото зовнішню адресу API
**не намагається видалити**: `keyFor` упізнає тільки адреси власного бакета.

Перехід `memory` → `r2` у dev не переносить фото. Ті, що лежали в пам'яті, і так зникли б з рестартом.
