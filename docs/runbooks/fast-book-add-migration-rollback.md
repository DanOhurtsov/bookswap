# Runbook — швидке додавання книжок: розгортання, відкат і ручна перевірка

Стосується міграцій плану [fast-book-add](../plan/fast-book-add.md), ред. 2 і 2.1 (§2, §6a):

| Міграція | Зміст | Тип |
|---|---|---|
| `20261001090000_fast_add_operations` | таблиця `LibraryAddOperation`, enum `LibraryAddTargetKind` | expand |
| `20261001100000_fast_add_edition_text_expand` | `Work.origLang`, `Edition.format` — nullable; `Edition.textKind` (nullable), `Edition.lang`; enum `EditionTextKind` | expand |
| `20261001110000_fast_add_edition_text_contract` | ідемпотентний backfill, `textKind NOT NULL`, CHECK `edition_translation_implies_translation_kind` | contract |
| `20261001120000_fast_add_external_refs` | таблиця `EditionExternalReference`, enum `ExternalBookSource`, зняття `DEFAULT PAPERBACK` з `Edition.format` | expand |

Золоте правило [catalog-correction-migration-rollback.md](./catalog-correction-migration-rollback.md) діє й тут: застосований `migration.sql` не редагується, `prisma migrate reset` не є способом «скасувати». Відкат — це відновлення з backup до відновлення записів або **нова forward-міграція** (§6). **Назвати зміни «сумісними» лише тому, що старі дані не видаляються, не можна:** сумісність визначається тим, що й коли пише кожна версія коду.

## 1. Доступні версії

**Погоджений і перевірений до розгортання лише один випуск: ця збірка одним пакетом із зупинкою записів (§3).** Існують рівно дві версії коду, між якими можна переходити:

| Версія | Що це | Міграції |
|---|---|---|
| **R0** | код і схема до цієї роботи (поточний стан) | до `20260930090000_stage10_reading_status` включно |
| **F** | ця збірка (етапи A–F) | усі чотири міграції таблиці вище |

**Проміжних релізів немає.** У межах цієї роботи не створювалося жодного коміту, тега чи збереженого артефакту «лише A», «A+B», «R2» або «R3», і жоден такий стан не проходив `./gate.sh` як окреме дерево. Тому **поетапне розгортання й відкат «на R2/R3» не підтверджені й не пропонуються**: їх не можна відтворити з репозиторію. Подібне розгортання можливе лише після того, як PO попросить зібрати проміжні дерева (кожне — окремим комітом з власним зеленим `./gate.sh`); до того схема сумісності нижче — довідка для майбутнього, а не інструкція.

### Довідка: чому поетапне розгортання потребувало б окремих збірок

Кожна міграція застосовується **до** нового коду (`db:deploy` → рестарт API → web), поки ще працює попередній API, тож мусить бути безпечною для попереднього коду:

- `…_fast_add_operations` і `…_external_refs` (таблиці) — безпечні для коду R0: він їх ігнорує.
- `…_edition_text_expand` — лише послаблює й додає; безпечна для R0, якщо жоден код не пише `null`/`UNKNOWN`.
- `…_edition_text_contract` робить `Edition.textKind` обов'язковим: код R0 вставляє видання без нього, і така вставка падає з `23502` (перевіряє `fast-add-text-migration.db-spec.ts`). Тому її можна застосовувати лише тоді, коли жоден інстанс не працює на R0, а код, що пише `textKind` явно, уже розгорнуто.
- Створення неповних записів (`null`, `UNKNOWN`) не можна вмикати раніше, ніж усі читачі навчилися їх читати.

Ці обмеження — причина, чому фінальна збірка розгортається одним пакетом (§3), а не «міграція під працюючий R0».


## 2. Перед розгортанням

1. **Backup.** `pg_dump -Fc`, файл поза сервером БД. Без нього не починати.
2. **Знімок кількостей** (для порівняння після):

   ```sql
   SELECT 'Edition' AS t, count(*) FROM "Edition"
   UNION ALL SELECT 'Work', count(*) FROM "Work"
   UNION ALL SELECT 'Copy', count(*) FROM "Copy"
   UNION ALL SELECT 'Loan', count(*) FROM "Loan"
   UNION ALL SELECT 'CatalogRevision', count(*) FROM "CatalogRevision";
   ```

3. **Усі інстанси `api` зупинені** (§3, крок 1): жоден код R0 не може вставити видання без `textKind` між backfill і `SET NOT NULL`. Перевірка: `SELECT count(*) FROM pg_stat_activity WHERE datname = current_database() AND application_name <> ''` не показує підключень API.
4. `prisma migrate status` не показує розбіжностей історії.

## 3. Порядок розгортання (єдиний погоджений: пакетом із зупинкою записів)

Не застосовувати міграції поверх працюючого R0, посилаючись на цей runbook: код R0 під час міграції вставляє видання без `textKind`.

1. Зупинити `api` (`docker compose stop api`); web показує недоступність. Записів у БД немає.
2. Backup (`pg_dump -Fc`), файл поза сервером БД, і знімок кількостей (§2). **Без перевіреного backup не починати.**
3. `pnpm db:deploy` — усі чотири міграції; backfill заповнює рядки R0.
4. Перевірки (§4): `textKind IS NULL` — 0; I1 і I2/I3 — без порушень; кількості зі знімка збігаються.
5. Запустити фінальні `api` + `web` (збірка F).
6. Smoke: додати наявне видання, повторити той самий `operationId` (має бути `replayed: true`), додати зовнішнє видання, відкрити «Налаштувати».
7. Відкриту вкладку зі старим бандлом перезавантажити (вона не знає про `null` у відповідях).


## 4. Перевірки після міграції (інваріанти)

Усі запити мусять повернути **0**:

```sql
-- після backfill легасі-рядків немає
SELECT count(*) FROM "Edition" WHERE "textKind" IS NULL;

-- I1: прив'язаний переклад ⇒ TRANSLATION (це ще й CHECK у БД)
SELECT count(*) FROM "Edition" WHERE "translationId" IS NOT NULL AND "textKind" <> 'TRANSLATION';

-- I2: мова прив'язаного видання = мова перекладу (виняток — навмисно введена людиною мова, її бути не може: PATCH узгоджує)
SELECT count(*) FROM "Edition" e JOIN "Translation" t ON t.id = e."translationId"
WHERE e."lang" IS DISTINCT FROM t."lang";

-- I3: оригінал на творі з відомою мовою має її мову (або мову не визначено)
SELECT count(*) FROM "Edition" e JOIN "Work" w ON w.id = e."workId"
WHERE e."textKind" = 'ORIGINAL' AND w."origLang" IS NOT NULL AND e."lang" IS NOT NULL
  AND e."lang" <> w."origLang";
```

Backfill відтворив рівно те, що старий код обчислював на льоту; для порівняння «до/після»: мова легасі-видання з перекладом = `Translation.lang`, без перекладу = `Work.origLang`. Знімок кількостей із §2 має збігтися; `Loan`, `Copy`, `CatalogRevision` не змінюються.

## 5. Конфігурація зовнішніх джерел

- `GOOGLE_BOOKS_API_KEY` — необов'язковий; без нього працюють публічні ліміти. Том за id (`GET /volumes/{id}`) і пошук за ISBN використовують той самий ключ.
- Таймаут одного звернення — `CATALOG_LOOKUP_TIMEOUT_MS` (за замовчуванням 5 с); він же обмежує вибірку тому. Відповіді: `504 CATALOG_LOOKUP_TIMEOUT`, `502 CATALOG_LOOKUP_PROVIDER_ERROR`, `404 CATALOG_LOOKUP_NOT_FOUND`. Нічого не записується; повтор із тим самим `operationId` безпечний.
- Окремий throttle-бакет `quickAdd`: `QUICK_ADD_RATE_LIMIT` (30) і `QUICK_ADD_RATE_WINDOW_MS` (60 с) на клієнта.
- Видання, відоме локально (за ISBN чи підтвердженим посиланням), **не потребує мережі** — недоступність провайдера його додавання не блокує.

## 6. Відкат

Версій для відкату рівно одна — **R0** — і лише у вікні **до того, як відновлено запис** (після кроку 5 §3 і до першого запису користувачів).

| Момент | Дія |
|---|---|
| Збій на кроках 3–4 (міграція чи перевірки), записи ще не відновлено | Лишити `api` зупиненим. Відновити БД з backup кроку 2 (`pg_restore`), розгорнути код R0, запустити. Нічого не втрачено: з моменту backup записів не було. |
| Збій на кроці 6 (smoke), записи користувачів ще не прийнято | Те саме: зупинити `api`, відновити backup, код R0. |
| Записи користувачів уже прийнято на збірці F | **Відкату на R0 немає:** код R0 не пише `textKind` (вставка падає після `…_contract`) і не вміє читати `null`/`UNKNOWN`, а відновлення backup втратило б нові дані. Виправлення — лише вперед: нова версія коду й/або нова forward-міграція, перевірена на наповненій scratch-БД за зразком `fast-add-text-migration.db-spec.ts`. Якщо потрібно зупинити нові входи — вимкнути `api`/web, а не міняти схему. |

Проміжних цілей відкату («R1», «R2», «R3») не існує (§1). Не прирівнювати «дані не видалено» до «старий код сумісний»: сумісність визначається тим, що й коли пише кожна версія коду.


## 7. Метрики (baseline перед rollout і порівняння після)

`BOOK_ADDED` зберігається як є; нових подій немає. Для часток і повторів — таблиця `LibraryAddOperation`:

```sql
-- Скільки додавань за днями й типом цілі (EXISTING_EDITION / EXTERNAL_EDITION / MANUAL)
SELECT date_trunc('day', "createdAt") AS day, "targetKind", count(*)
FROM "LibraryAddOperation" GROUP BY 1, 2 ORDER BY 1, 2;

-- Частка ручних і зовнішніх (вперше потрапили в каталог) у загальній кількості додавань
SELECT "targetKind", count(*)::float / sum(count(*)) OVER () AS share
FROM "LibraryAddOperation" GROUP BY "targetKind";

-- Видалені результати (операція є, примірника вже немає)
SELECT count(*) FROM "LibraryAddOperation" WHERE "copyId" IS NULL;

-- Скільки видань уточнено після автозаповнення: ревізії видань, створених через швидке додавання
SELECT count(*) FROM "CatalogRevision" r
JOIN "LibraryAddOperation" o ON o."editionId" = r."entityId"
WHERE r."entityType" = 'EDITION' AND o."targetKind" = 'EXTERNAL_EDITION';
```

Не інструментуються (потрібна окрема подія): час від вибору результату до підтвердженого додавання, частка завершених без відкриття деталей, кількість повторних мережевих запитів без повторного `Copy`. До появи baseline цілі часу не встановлюються (план §9).

## 9. Ручна перевірка в реальних браузерах (NOT RUN)

Автоматичні тести jsdom підтверджують стани, обробники клавіатури, Escape і керування фокусом у межах можливостей середовища. **Реальна адаптивна верстка, прокрутка, touch-взаємодія і браузерна поведінка фокуса ними не підтверджуються.** Playwright не додавався (рішення PO). Статус кожного пункту — `NOT RUN`, доки його не виконано й не записано `PASS`/`FAIL` із пристроєм і версією.

Синтетичні дані; реальні персональні дані заборонені (D2).

| ID | Перевірка | Пристрої | Статус |

| M2 | «Налаштувати»: на desktop панель праворуч (~440 px), на телефоні — нижня панель, що прокручується; довга назва не ламає макет | те саме | NOT RUN |
