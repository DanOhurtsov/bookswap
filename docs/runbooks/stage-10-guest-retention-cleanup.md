# Runbook — retention-чистка гостьових контактів (Етап 10, крок 10h)

Джерело: [execution plan Етапу 10, §0.7/§0.7.1/§0.9/§6.11](../plan/stage-10-real-world-history.md#611-retention-d3--механізм-виконання-t7).

> **D2 — відкритий release blocker.** Цей крок реалізує лише строк зберігання приватного alias
> (retention, D3) і механізм чистки — він **не** є правовою підставою BookSwap для обробки даних
> гостя і **не знімає** D2. Реальні персональні дані гостя заборонені в усіх середовищах.

## Що робить чистка

`ExternalBorrower.retainUntil` перераховується **транзакційно** при створенні контакту, створенні
гостьової позики та переходах `return`/`mark_lost`/`recover`/`close_loss` (`GuestLoanService`,
`ExternalBorrowersService` — `apps/api/src/external-borrowers/retention.ts`). Формула — §0.9 плану:

- активна позика (`HANDED_OVER`/`PENDING_CONFIRMATION`) → `retainUntil = NULL`;
- контакт без жодної позики → `createdAt + 90д`;
- інакше — `max()` по всіх позиках контакту: `RETURNED` дає `returnedAt + 90д`; закрита
  (`RECOVERED`/`LOSS_CLOSED`) `LOST` дає `closedAt + 90д` (від **першої** за часом події закриття);
  ще не закрита `LOST` дає `LOAN_LOST.occurredAt + 365д` — кожна незакрита `LOST` окремо.

Сам перерахунок **не видаляє** контакт — лише встановлює момент, коли видалення стає
**допустимим**. Видалення — окрема, ідемпотентна дія: CLI-команда
`apps/api/src/cli/guest-contact-retention-cleanup.ts`.

## Виконавець — CLI + зовнішній scheduler (Q1)

Затверджено Product Owner ([§0.9 плану](../plan/stage-10-real-world-history.md#09-рішення-product-owner-щодо-q1-q2-і-q3a-виконання-retention-і-межа-для-нескінченно-незакритої-втрати)):
чистку виконує **CLI-команда**, яку **щодня** запускає **зовнішній** scheduler (поза процесом
API) — **не** інтервальний сервіс у процесі API (варіант, застосований для
`SessionCleanupService`/`InviteEmailHashCleanupService`, тут явно **відхилений**).

**Платформа розгортання API ще не обрана.** Цей runbook **не стверджує**, що зовнішній scheduler
уже налаштований чи запущений будь-де — це залишається окремою дією оператора Етапу 11.

### Запуск

```bash
pnpm --filter @bookswap/api run retention:guest-contacts
```

Команда збирає застосунок (`pnpm run build`) і запускає `dist/cli/guest-contact-retention-cleanup.js`
— NestJS application context без HTTP-шару, диспетчера сповіщень чи дайджесту (той самий принцип,
що `merge-cli.module.ts`). Читає `DATABASE_URL`/`DIRECT_DATABASE_URL` з кореневого `.env` (той
самий механізм, що й решта CLI-команд, `validateEnv`).

Для production/beta-розгортання (коли платформу буде обрано) зовнішній scheduler повинен:

1. Мати доступ до того самого `DATABASE_URL`, що й API-процес.
2. Запускати `node dist/cli/guest-contact-retention-cleanup.js` (попередньо зібраний тим самим
   білдом, що й API) **щодня**, у будь-який час доби — порядок виконання відносно інших
   background-процесів не важливий (чистка не залежить від `BACKGROUND_MODE`, вона взагалі поза
   процесом API).
3. Трактувати ненульовий exit code як збій запуску (алертинг/ретрай за політикою оператора —
   деталі політики ретраю самим цим кроком не встановлюються, це технічна деталь виконавця).

### Негайний запуск після відновлення з backup

**Обов'язково**, одразу після кожного `pg_restore`/відновлення БД зі знімку: відновлення повертає
раніше стерті `ExternalBorrower`-рядки (backup зроблено до їхнього видалення) — наступний прохід
прибирає їх знову, ідемпотентно. Крок runbook-у Етапу 11 (відновлення з backup) повинен явно
включати виклик цієї команди одразу після відновлення, до відкриття доступу.

### Idempotency (RET6)

Повторний запуск того самого дня — безпечний no-op для вже опрацьованих контактів: жодного
подвійного видалення, жодної помилки. Два одночасні запуски (наприклад, ручний запуск оператора
збігся зі scheduler-ом) також безпечні — `FOR UPDATE SKIP LOCKED` по пачках (`BATCH_SIZE = 200`,
`guest-contact-retention-cleanup.service.ts`) розводить їх без взаємного очікування.

### Дві фази одного проходу

1. **Backfill.** Контакти з `retainUntil IS NULL` (створені до появи цього перерахунку в
   10f.2/10f.3/10g, чи з будь-якої іншої причини пропущені) — перераховуються за тією самою
   формулою, виключно з уже наявних `Loan`/`LoanEvent` (жодної вигаданої дати).
2. **Cleanup.** Контакти з `retainUntil <= now` видаляються разом з alias; `Loan`/`LoanEvent`
   лишаються без контакту (`borrowerContactId`/`heldByContactId` → `NULL` за FK, `borrowerKind`
   лишається `GUEST`).

Backfill іде **перед** cleanup у тому самому проході: щойно перерахований `retainUntil`, який
виявляється вже в минулому, стає кандидатом на видалення в цьому ж запуску.

**Доповнення 10i.1.** Скасована помилкова гостьова передача (`Loan = CANCELLED`) додає до формули доданок
`occurredAt першої події GUEST_HANDOVER_CANCELLED + 90д` (Q26); відсутня така подія — порушення цілісності, чистка
падає гучно, а не вигадує дату. Cleanup додатково локає рядки `GuestLoanConfirmation` контакту (порядок
`ExternalBorrower → Copy → Loan → GuestLoanConfirmation`); підтверджені гостем нікнейм/email видаляються разом із
контактом. Контакт із відкритим запитом підтвердження (`PENDING_CONFIRMATION`) — активна позика й не видаляється.

### Незалежність від `GUEST_LOANS_ENABLED`

Чистка **не** перевіряє прапорець функції: вимкнення гостьових позик зупиняє лише HTTP-ендпоінти
(`GuestLoansEnabledGuard`), не існування вже записаних контактів. Вимкнена функція не повинна
зупиняти видалення того, що вже назбиралося.

### Вивід і приватність

Stdout друкує лише кількості (`Перераховано retainUntil: N`, `Видалено гостьових контактів: M`).
Stderr на помилці друкує рядок `Тип помилки: <клас помилки>` (напр. `PrismaClientKnownRequestError
(код P2028)`, `PrismaClientInitializationError`) — **не** `.message`/`.stack` самої помилки: для
Prisma-помилок ці поля нерідко містять текст SQL-запиту й/або значення параметрів (тут це потенційно
alias чи contactId), а runbook прямо обіцяє їх відсутність. Класифікаційний `code` Prisma (коли є) —
стала невелика множина технічних кодів (`P1001`, `P2025` тощо), не дані запиту. За потреби — ще й
попередження про примусове завершення з'єднання (нижче). **Жодного alias, id контакту, значення
параметра запиту чи іншого PII** ні в stdout, ні в stderr, ні в логах Nest (команда піднімається з
`logger: false`). Перевірено db-spec-тестом, що фактично спричиняє збій і читає реальний stderr
зібраної команди (`guest-contact-retention-cleanup-cli.db-spec.ts`).

Повний текст помилки для діагностики (якщо `code`/клас недостатньо) лишається лише в реальних,
окремо керованих логах інфраструктури БД/оркестрації (Postgres server log, платформа розгортання) —
не в цьому CLI.

### Коди виходу й закриття ресурсів (shutdown policy, затверджена PO)

Три етапи, кожен оброблений контрольовано (`executeCleanupRun`,
`guest-contact-retention-cleanup.ts`): створення Nest application context → `run()` (сама чистка)
→ закриття (`app.close()`). Кожен здатен провалитися незалежно, і кожен дає безпечне повідомлення
(лише клас помилки, див. вище) замість сирого виводу.

- **`0`** — усі три етапи завершилися успішно, включно з підтвердженим закриттям. Рядки успіху
  (`Перераховано retainUntil: N`, `Видалено гостьових контактів: M`) друкуються лише ПІСЛЯ
  підтвердженого закриття — ніколи раніше, і ніколи, якщо закриття не підтверджене.
- **`1`** — збій на БУДЬ-ЯКОМУ з трьох етапів:
  - контекст не створився (напр. невалідне оточення) — `run()` і закриття навіть не
    намагаються;
  - `run()` завершився помилкою, але закриття все одно відбувається штатно (пачкова обробка:
    транзакція на пачку гарантує, що вже опрацьовані пачки лишаються опрацьованими; пачка, у
    якій сталася помилка, відкочується цілком — напівстертих даних не буває);
  - закриття відхилилося АБО не встигло за бюджет (нижче) — **навіть якщо `run()` до цього
    відпрацював успішно**: успіх чистки не скасовує збій закриття ресурсів, код виходу все одно
    `1`, а не `0`.

**Бюджет закриття — 5000 мс (затверджено PO).** Якщо `app.close()` встигає й не відхиляється —
процес виходить звичайним шляхом (без явного `process.exit()`, лише `process.exitCode`) — Node сам
завершується, щойно event loop порожній. Якщо `app.close()` відхиляється АБО не встигає за
бюджет — одне безпечне технічне повідомлення в stderr (`Закриття ресурсів не завершилося за 5000
мс — примусове завершення`, або клас помилки закриття) і ПРИМУСОВЕ `process.exit(1)` — єдине
місце в цьому файлі, де таке завершення взагалі відбувається. Причина: спільний `PrismaService`
(не власна поведінка цього CLI, і не змінюється цим кроком) на пулі, що ніколи не підключився, не
повертає керування з `$disconnect()` самостійно — без цього бюджету CLI повис би назавжди при
повністю недосяжній БД.

Окремо: створення контексту (`NestFactory.createApplicationContext`) викликається з
`abortOnError: false` — без цього прапорця NestJS сам, зсередини власного bootstrap-механізму,
викликає `process.exit(1)` на будь-якій фатальній помилці ініціалізації, МОВЧКИ, до того, як код
цього CLI взагалі побачить помилку. З прапорцем — таку помилку ловить сам `executeCleanupRun` і
друкує контрольоване повідомлення, як і для решти двох етапів.

## Що це НЕ вирішує

- **D2 лишається відкритим release blocker.** Строк зберігання приватного alias і механізм
  виконання — не правова підстава для обробки даних гостя.
- **Максимальний строк зберігання контакту в цілому** (не однієї конкретної `LOST`-позики) цим
  кроком **не визначено** — активна позика того самого контакту здатна відкладати чистку
  необмежено довго (§0.9 плану, докладно).
- Ручний `DELETE` контакту (`DELETE /me/external-borrowers/:id`) лишається окремою, суворішою
  передумовою (Q3d): заборонений при активній позиці чи будь-якій незакритій `LOST`, **навіть
  після** спливу її 365-денної межі. 365-денна межа відкриває шлях лише цій автоматичній чистці.
- Пакетна обробка, розмір пачки, `FOR UPDATE SKIP LOCKED`, точний CLI-інтерфейс і формат
  логу/виводу — інженерні деталі цього кроку (T7, пропозиція), не окремо затверджене продуктове
  рішення.
