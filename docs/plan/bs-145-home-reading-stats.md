# BS-145 — статистика читання на головній замість окремого «Списку читання»

Статус: реалізовано на гілці `codex/bs-145-home-reading-stats`, очікує незалежного рев'ю. Залежність: BS-140
(PR #74, змерджено).

## Постановка

Окремий приватний екран «Список читання» (`/reading-list`, Stage 10, 10j.2) прибирається з навігації.
Натомість головна показує авторизованому користувачеві статистику його особистих статусів читання:
скільки творів «Не читав», «Читаю» і «Прочитано». Статуси й далі встановлюються контролами BS-140 на
полиці, на сторінці власної книги та на сторінці твору.

## Погоджені правила статистики

1. Статус належить парі `userId + Work`, як у `WorkReadingStatus`.
2. Наявні статуси: `NOT_READ` — «Не читав», `READING` — «Читаю», `READ` — «Прочитано».
3. Рахуються всі явно встановлені особисті статуси користувача, включно з позиченими, архівними та вже
   відсутніми в бібліотеці книгами.
4. Один твір рахується один раз незалежно від видань і примірників.
5. Відсутність запису — статус не встановлено; у лічильники не входить. Явний `NOT_READ` входить.
6. Наявні записи, значення та `updatedAt` зберігаються. Backfill, міграцій і нових статусів немає.
7. Архівування, видалення примірника чи повернення позики не видаляють особистий статус і не виключають
   його зі статистики.

## A. Навігація та стара адреса

- Пункт «Список читання» прибирається з меню аватара (єдине місце, де він був; компактне меню й
  головний хедер його не мали). Меню: «Профіль», «Друзі», перемикач теми, «Вийти».
- `/reading-list` — серверний `redirect('/library')` у `page.tsx`. Старі query-параметри не переносяться
  (адреса призначення фіксована; редирект через `next.config` переніс би їх). Для прямого запиту це
  HTTP-відповідь 307 без HTML старого екрана; для клієнтської навігації — той самий редирект у RSC.
- Гість: `/reading-list` → `/library`, далі звичайний захист бібліотеки.
- Видаляються `ReadingListScreen`, `useReadingList`, `fetchReadingList` і їхні експорти та тести.
- Лишаються `ReadingStatusPanel`, `ShelfReadingStatus`, керування статусами й увесь backend
  `GET /me/reading-list` з контрактами та API-регресіями.

## B. Серверна статистика

- `GET /api/v1/me/reading-stats` у модулі `reading-status`, під `SessionGuard`. Входу немає: користувач
  лише із сесії, сторонні query-параметри (зокрема `userId`) ігноруються й ні на що не впливають.
- Відповідь: `{ counts: { NOT_READ, READING, READ } }` — цілі невід'ємні числа, усі три ключі завжди
  присутні. Схема `readingStatsResponseSchema` — у `packages/shared`.
- Підрахунок — один SQL-запит `GROUP BY status` за всіма рядками `WorkReadingStatus` користувача; кількість
  запитів не залежить від кількості творів. Унікальність `(userId, workId)` означає, що кожен твір —
  один рядок, тож видання й примірники лічильники не множать.
- Merge: `MergeService` переносить статуси на канонічний твір і прибирає дублі, а запис статусу
  блокує `Work FOR SHARE` (BS-140), тож рядків на злитих творах немає і кожен остаточний твір рахується
  один раз. Окремого фільтра в запиті не потрібно; це перевіряє e2e.
- Нового серверного кешу немає.

## C. Головна сторінка

- `app/page.tsx` лишається Server Component із тонкою композицією: читає знімок статистики на сервері й
  передає його клієнтському листку `HomeReadingStats`. Решта вмісту головної не змінюється.
- Серверне читання (`fetchReadingStatsSnapshot`, `server-only`, за зразком `fetchActivationProgress`):
  - без cookie — гість, жодного запиту до API;
  - спершу `GET /auth/session`: 401 — гість, і приватний API статистики не викликається; так знімок
    отримує `userId` того, для кого його прочитано;
  - далі `GET /me/reading-stats` з тим самим cookie; відповідь розбирається спільною схемою;
  - `cache: 'no-store'`; помилки не логуються й не передаються (можуть містити cookie).
  - `headers()` робить маршрут динамічним: під час build приватний API не викликається.
- Знімок — `{ status: 'ready', userId, data } | { status: 'guest' } | { status: 'error' }`.
- Клієнт:
  - сесія ще завантажується — стан завантаження (для серверного гостя — нічого); знімок не показується
    й не пишеться в кеш, доки браузер не підтвердить, чия це вкладка: якщо сесія змінилася після
    рендеру сторінки, знімок належить іншій людині. Серверне читання все одно економить клієнтський
    запит статистики;
  - гість або помилка сесії — блоку немає, запитів немає;
  - авторизований — тіло монтується з ключем `userId` і читає `['reading-stats', userId]` через
    TanStack Query; знімок стає `initialData` лише якщо його `userId` збігається з сесією. `initialData`
    застосовується лише до ще не створеного запису, тож наявні (новіші) дані не перезаписуються;
  - `gcTime: Infinity` для цього ключа: інакше після 5 хв на іншій сторінці запис зник би, і старий
    RSC-знімок із back/forward-кешу Next засіяв би його знову як свіжий. Кеш і так очищається при зміні
    акаунта;
  - `retry: false`; помилка — повідомлення й кнопка «Спробувати ще раз»; помилка ніколи не показує нулі;
  - запис, позначений застарілим після збереження статусу, під час перечитування показується як
    завантаження, а не старими числами.
- Стани: завантаження, помилка з явним повтором, порожній стан (жодного встановленого статусу) з
  посиланням на `/library`, готовий стан з усіма трьома лічильниками, зокрема нульовими.

## D. Синхронізація після зміни статусу

- Один canonical-ключ `['reading-stats', userId]`.
- Після підтвердженого `PUT` (будь-який контрол — усі йдуть через `useReadingStatus`) спершу скасовуються
  запити статистики в дорозі, потім точково інвалідується цей ключ. Не очікується мутацією: помилка
  перечитування не перетворює збереження на помилку, а pending не подовжується.
- Активний запис перечитується одразу; незмонтований — позначається застарілим і перечитується при
  поверненні на головну. Скасування в дорозі не дає пізній відповіді, що стартувала до `PUT`, записатися
  поверх (вона ж скинула б позначку «застаріле»).
- Невдалий `PUT` нічого не інвалідує. Повторне встановлення того самого статусу `PUT` не надсилає (BS-140).
- Зміна акаунта / logout: ключ містить `userId`, `Providers` очищає кеш, тіло монтується з ключем
  `userId`, а знімок іншого користувача не використовується.
- Виправлення BS-140 (canonical Work, спільний pending, захист від повторної зміни, очищення кешу сесії)
  не змінюються. Немає повного reload, polling чи глобального `invalidateQueries()`.

## Виправлення після рев'ю (P2)

Дефект: якщо головна ще не монтувалася, запису `['reading-stats', userId]` не було, і `PUT` не лишав
жодної ознаки застарілості. Перехід на головну, чию статистику сервер прочитав до збереження, засівав кеш
старим знімком як свіжим (у браузері — «Читаю 1», «Прочитано 0» без нового `GET`, хоча в БД `READ`).

Виправлення (`features/reading-status/model/use-reading-stats.ts`):

- `refreshReadingStats` після скасування запитів у дорозі створює запис статистики, якщо його немає
  (порожній, без чисел, з тими самими параметрами, зокрема `gcTime: Infinity`), і лише потім точково
  інвалідує ключ. Позначка «застаріле» тепер є навіть без жодного читання; мережевого запиту при цьому
  немає.
- `useReadingStats` не передає серверний знімок як `initialData` у запис із цією позначкою: невідомо,
  прочитано знімок до чи після збереження. TanStack застосовує `initialData` і до наявного запису без
  даних, тож самого порожнього запису було б замало. Такий запис показує завантаження й читає статистику
  один раз. Позначка переживає невдале чи скасоване читання; знімає її лише успішне.
- Звичайний сценарій без збереження не змінився: знімок засіває кеш без запиту. Ціна виправлення — один
  `GET` при першому відкритті головної після збереження в цій вкладці.
- Невдалий `PUT` нічого не позначає. Ключ і далі містить `userId`, а `Providers` очищає кеш при зміні
  акаунта.

Регресії (падали до виправлення, проходять після): `HomeReadingStats.sync.spec.tsx`, блок «the first
mount of home after a save…», і браузерний сценарій у `home-reading-stats.browser-spec.ts` — справжня
відповідь `ReadingStatusService.stats` для переходу на головну затримується тестом, поки на видимій
бібліотеці зберігається новий статус.

## Рішення, прийняті в межах задачі

- Редирект тимчасовий (307, `redirect`), а не постійний (308): браузери кешують 308 назавжди, тож
  повернути адресу було б неможливо. Якщо потрібен 308 — це одна заміна на `permanentRedirect`.
- Порожній стан замінює три нульові лічильники повідомленням і посиланням на бібліотеку.
- Знімок показується лише після підтвердження сесії: прив'язка до користувача важливіша за кілька
  десятків мілісекунд першого paint з числами.
- Невдале серверне читання не є «нулями»: браузер один раз читає сам (`retry: false`), а якщо й це не
  вдалось — помилка з повтором.
- `docs/functional-specification.md` оновлено в рядках про меню аватара та маршрут `/reading-list`.

## Критерії готовності та перевірки

- API (`apps/api/test/reading-stats.e2e-spec.ts`): 401 без сесії; ізоляція користувачів і ігнорування
  `userId`; порожній результат; усі три статуси; явний `NOT_READ` проти відсутності запису; кілька
  видань/примірників; статуси поза поточною бібліотекою (архів, видалений примірник, повернена позика);
  merge; незмінність записів і `updatedAt`; один SQL-запит незалежно від кількості творів.
- Shared: схема відповіді.
- Web: навігація без пункту; редирект (зокрема з query); серверний знімок; view-model; блок головної
  (loading/error/retry/empty/нульові лічильники, гість); синхронізація з контролами, перший `NOT_READ`,
  невдалий `PUT`, пізня відповідь, незмонтована головна; зміна сесії зі справжніми `SessionProvider` і
  `Providers`.
- Браузер (реальні Next/API, тестова БД): головна → бібліотека → зміна → головна без перезавантаження;
  зміна на сторінці власної книги й твору; пряма стара адреса; мобільна ширина, світла/темна теми,
  клавіатура й фокус; оновлений `reading-status-flow.browser-spec.ts`.
- `pnpm lint`, `pnpm typecheck`, `./gate.sh`.
