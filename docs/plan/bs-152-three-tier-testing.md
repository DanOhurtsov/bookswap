# BS-152 — трирівнева стратегія тестування

Статус: реалізовано на гілці `codex/bs-152-three-tier-testing`, виправлення після рев'ю.
Окремий ruleset [main_full_test_suite](https://github.com/DanOhurtsov/bookswap/rules/26453772)
активний: `Full test suite` від GitHub Actions обов'язковий для `main`, без bypass, з вимогою
актуальності гілки. Нова конфігурація workflow ще очікує першого віддаленого прогону.

## Постановка

Під час розробки тести мають бути швидкими й не вичерпувати пам'ять WSL, а перед merge — повними.
Раніше `pnpm test` і `gate.sh` запускали всі unit-тести з Jest за замовчуванням: `cores − 1` = 15 воркерів у
Shared і API (Web мав власний ліміт 4). Інтеграційні тести (E2E, DB) були лише в `gate.sh` і CI, браузерні —
лише в CI.

Тепер є три рівні; рівень визначає **лише обсяг тестів**, решта перевірок (`format:check`, lint, typecheck,
build, Git-гігієна, незмінність `docs/specification.md`) виконується в `gate.sh` на кожному рівні.

| Рівень       | Команда              | Що запускає                                                                             | Коли                                    |
| ------------ | -------------------- | --------------------------------------------------------------------------------------- | --------------------------------------- |
| **Fast**     | `pnpm test:fast`     | unit-тести, яких можуть торкатися зміни гілки (див. [межі](#межі-fast))                 | під час розробки                        |
| **Standard** | `pnpm test` (= `pnpm test:standard`) | усі unit-тести: Shared, Web, API Unit + тести самого інструмента рівнів | перед комітом; `./gate.sh` за замовчуванням |
| **Full**     | `pnpm test:full`     | Standard + міграції й seed тестової бази + E2E + DB + browser                                 | перед merge; CI на кожен push і PR      |

Єдине джерело правди про склад рівнів — `tools/test-tiers/suites.mjs`; `pnpm test:*`, `gate.sh` і CI
викликають один і той самий `tools/test-tiers/run.mjs`.

вихідна оцінка задачі — 7 064 тести / 407 файлів, ~5 162 Standard — виявилася застарілою):

| Набір      | Конфігурація                       | Файлів | Тестів | Рівень          |
| ---------- | ---------------------------------- | -----: | -----: | --------------- |

| Web        | `apps/web/jest.config.js`          |    184 |  2 699 | Standard, Full  |
| API Unit   | `apps/api/jest.config.js`          |     93 |  2 214 | Standard, Full  |
| Інструмент | `node --test tools/test-tiers/*.test.mjs` |  6 |     66 | Standard, Full  |
| E2E        | `apps/api/test/jest-e2e.json`      |     93 |  1 608 | Full            |
| DB         | `apps/api/test/jest-db.json`       |     33 |    266 | Full            |
| Browser    | `apps/api/test/jest-browser.json`  |     13 |    144 | Full            |

Разом 446 spec-файлів Jest і 7 630 тестів Jest (Standard — 307 файлів / 5 612 тестів) плюс 66 тестів
інструмента (після налаштування CI). Що жоден не загубився, перевіряє `tools/test-tiers/wiring.test.mjs`: кожен
`*.spec.ts(x)`, `*.e2e-spec.ts`, `*.db-spec.ts`, `*.browser-spec.ts` репозиторію (tracked і untracked)
належить **рівно одному** набору з таблиці, Standard містить лише три unit-набори, Full — усі.

## Команди

```
pnpm test:fast [-- <аргументи Jest>]                 # Fast
pnpm test:fast --base origin/release [-- …]           # Fast від іншої бази
pnpm test  /  pnpm test:standard [-- <аргументи Jest>] # Standard
pnpm db:up && pnpm test:full                          # Full
./gate.sh [--level fast|standard|full]                # перевірка; рівень за замовчуванням — standard
node tools/test-tiers/run.mjs <рівень> --dry-run      # показати команди без запуску
```

Невідомий рівень чи аргумент — exit code 2 з підказкою (і в `run.mjs`, і в `gate.sh`). Будь-який
провалений крок зупиняє прогін, його exit code стає exit code раннера, а невиконані кроки перелічуються
як «не виконано» — частковий прогін не виглядає зеленим.

Standard і Full у `gate.sh` та CI ідуть з `--force`: кеш Turbo не підміняє реального прогону. Локальний
`pnpm test` без `--force` може відтворити кешований результат Turbo — лише для ідентичних входів задачі.

## Fast

### База

1. `--base <ref>` або змінна `BOOKSWAP_TEST_BASE`. Якщо ref не існує — помилка (exit 2), а не мовчазна
   заміна на іншу базу.
2. Інакше перша наявна з `origin/main`, `main`.
3. Від бази береться **merge-base** з `HEAD`: коміти, що потрапили в `main` після відгалуження, не
   вважаються змінами гілки.

Зміни = `git diff --name-status --no-renames <merge-base>` (закомічені на гілці + staged + unstaged,
включно з видаленнями) + `git ls-files --others --exclude-standard` (untracked, крім ignored).
Перейменування приходить як видалення старого шляху й додавання нового. Раннер друкує базу, merge-base
і вибрані набори з причинами.

Якщо бази немає (наприклад, shallow clone без `main`) або аналіз падає з будь-якої причини, Fast
**розширюється до Standard** і пише причину. Хибного «нічого не зачеплено» з помилки аналізу не буває.

### Правила вибору

| Змінений файл                                                                  | Що запускається                                                       |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `docs/**`, будь-який `*.md`                                                    | нічого                                                                |
| будь-що поза пакетами (`package.json`, lockfile, `turbo.json`, `tsconfig.base.json`, `tools/**`, `gate.sh`, `.github/**`, `eslint.config.mjs`, …) | увесь Standard |
| модуль (`.ts/.tsx/.js/.mjs/.cjs/.json`) у roots Jest пакета                    | тести, пов'язані з ним за графом імпортів (`jest --findRelatedTests`) + «файлові» тести пакета |
| файл у корені пакета (`package.json`, `jest.config.js`, `tsconfig*.json`, `next.config.ts`, …) | увесь набір пакета                                    |
| не-модуль у пакеті (`.css`, `.prisma`, `.sql`, `.csv`, зображення, …)          | увесь набір пакета — граф Jest такі залежності не бачить               |
| модуль поза roots Jest пакета                                                  | увесь набір пакета                                                    |
| видалений модуль (зокрема перейменований)                                       | увесь набір пакета — імпортерів видаленого файлу граф Jest уже не знайде |
| видалений тест                                                                 | нічого                                                                |
| не-тестовий файл пакета, від якого залежать інші пакети (`@bookswap/shared`)   | **увесь** набір кожного транзитивного споживача (Web, API) — споживачі імпортують `dist`, а не вихідні файли, тож граф Jest у них змін не бачить |
| файл, оголошений у `turbo.json` входом test-задачі іншого пакета (`$TURBO_ROOT$/…`, зараз — шаблони імпорту в `apps/web/public`) | увесь набір пакета-споживача (API) |

Граф workspace-залежностей читається з `package.json` пакетів, roots — з `jest --showConfig`, крос-пакетні
входи — з `turbo.json`. Окремого графа залежностей інструмент не будує: усередині пакета вибір робить Jest,
між пакетами — оголошені workspace-залежності.

**«Файлові» тести.** Тест, що імпортує `fs`, `fs/promises`, `child_process` або `eslint`, читає вихідний код
чи запускає інструмент повз граф імпортів (список маршрутів через `readdirSync`, ESLint по фікстурах).
Такі тести додаються до кожного Fast-прогону свого пакета. Зараз їх 14 (10 у Web, 4 в API). Найдорожчий —
`apps/web/eslint-fixtures/import-rules.spec.ts` (~25 с): він лінтить тимчасові файли, що імпортують реальні
модулі web, тож справді залежить від коду web. Через нього будь-яка зміна Web у Fast коштує щонайменше ~26 с.

Перед тестами Fast збирає залежності вибраних пакетів (`turbo run build --filter=<пакет>^...`) і генерує
Prisma Client (`turbo run generate`) — з кешем Turbo це секунди. Пакети йдуть по черзі.

### Межі Fast

Fast — інструмент розробки, а не доказ. Він **ніколи** не запускає E2E, DB і browser і щоразу друкує,
які з них зміни можуть зачепити:

- E2E і DB — будь-яка зміна в `@bookswap/api` або його залежностях (`@bookswap/shared`);
- browser — те саме плюс будь-яка зміна в `@bookswap/web` (браузерні тести запускають `next dev`).

Що Fast принципово не бачить:

- ignored-файли (`.env`, згенерований Prisma Client, `dist`) — Git їх не показує;
- залежність тесту від файлу, яку виражено не імпортом і не через `fs`/`child_process`/`eslint`
  (наприклад, через бібліотеку glob) — евристика «файлових» тестів її не розпізнає;
- залежність між пакетами через файлову систему, не оголошену в `turbo.json`;
- поведінку, що залежить від часу, оточення чи порядку тестів.

Тому перед merge обов'язковий Full, а перед комітом — Standard.

## Standard

`turbo run test --concurrency=<BOOKSWAP_TEST_CONCURRENCY> -- --maxWorkers=<BOOKSWAP_JEST_WORKERS>` (тобто
пакетний `jest` кожного з трьох пакетів) + `node --test tools/test-tiers/*.test.mjs`. E2E, DB і browser не
входять. Кореневі скрипти викликають раннер, раннер — пакетні `jest`; жоден пакетний скрипт не викликає
кореневий, і в `turbo.json` немає кореневої задачі `//#test` — рекурсії немає (перевіряє
`wiring.test.mjs`).

**Pre-commit.** Версіонований `.githooks/pre-commit` запускає `pnpm test:standard --force`.
Встановлення для кожного checkout: `pnpm hooks:install`; команда встановлює executable-біт і локальний
`core.hooksPath=.githooks`, не змінює глобальний Git-конфіг та відмовляється замінювати наявний чужий хук.
Нових залежностей немає. У поточному WSL checkout хук встановлений і перевірений. Решта quality checks —
у `./gate.sh`; перед merge — обов'язковий Full у CI.

## Full

Кроки, послідовно, перший провал зупиняє прогін:

1. **unit** — як Standard, завжди з `--force`;
2. **db-setup** — Prisma Client, збірка залежностей API, `pnpm --filter @bookswap/api test:prepare-db`.
   Наявний fail-closed guard перевіряє `TEST_DATABASE_URL` до підключення, після чого тестова база
   перестворюється, міграції застосовуються з нуля, а seed CLI запускається двічі. Обидва URL для seed
   явно підмінені на тестовий; dev-база не мігрується й не наповнюється. Інтеграційні набори потім
   перестворюють тестову базу, тому smoke-дані seed не потрапляють до тестів;
3. **e2e** — `turbo run test:e2e`;
4. **db** — `turbo run test:db-specs` (залежить від збірки API: `guest-contact-retention-cleanup-cli.db-spec`
   запускає зібрану CLI);
5. **browser** — `turbo run test:browser`.

`pnpm test:db` лишився (`test:e2e` + `test:db-specs`) для тих, хто звик до нього.

**Підготовка.**

- PostgreSQL: `pnpm db:up` (`./gate.sh --level full` робить це сам). У CI — service-контейнер.
- `.env` у корені з `DATABASE_URL`, `DIRECT_DATABASE_URL`, `TEST_DATABASE_URL` (див. `.env.example`).
- Chromium для `playwright-core` **разом із системними бібліотеками**:
  `pnpm --filter @bookswap/api exec playwright-core install --with-deps chromium` (системна частина
  потребує `sudo`; у CI так і зроблено). Відсутній Chromium або бібліотека — **падіння** browser-кроку, а не
  пропуск. У WSL 03.11.2026 встановлено відсутній `libasound2t64` і `libasound2-data`;
  перевірка headless-запуску Chromium успішна. Початкове падіння збережене нижче як історичний benchmark.

**Ізоляція тестової бази.** E2E, DB і browser працюють лише з `TEST_DATABASE_URL`, яку `globalSetup` дропає
й створює заново. Перед будь-яким підключенням `apps/api/test/db/guard.ts` fail-closed перевіряє, що це
локальна база з суфіксом `_test`, яка не збігається з робочою; будь-яке порушення — падіння кроку з
ненульовим кодом. Інтеграційні конфіги лишаються з `maxWorkers: 1`: файли ділять одну базу.

## gate.sh

```
./gate.sh                  # = --level standard
./gate.sh --level fast     # також --level=fast
./gate.sh --level full
```

Порядок: `format:check` → `lint` + `typecheck` → `build` → тести рівня → Git-гігієна → незмінність
`docs/specification.md` → `git status`. Збірка тепер іде **до** тестів (раніше після): Full запускає зібрану
CLI API, і так вона береться з кешу щойно зробленої `build --force`, а не збирається вдруге. Збірка й тести,
як і раніше, ніколи не йдуть паралельно. `pnpm db:up` — лише на рівні `full`. `gate.sh` нічого не
форматує, не виправляє й не комітить.

## Контроль ресурсів

| Змінна                       | За замовчуванням        | Що обмежує                                                        |
| ---------------------------- | ----------------------- | ----------------------------------------------------------------- |
| `BOOKSWAP_JEST_WORKERS`      | `min(4, CPU − 1)`, ≥ 1  | `--maxWorkers` кожного unit-набору (перекриває `maxWorkers` конфігів) |
| `BOOKSWAP_TEST_CONCURRENCY`  | `1`                     | скільки пакетів Standard/Full-unit виконуються одночасно          |
| `BOOKSWAP_TURBO_CONCURRENCY` | `2`                     | `--concurrency` Turbo для lint/typecheck/build і залежностей інтеграційних кроків |

- Значення — ціле ≥ 1 і не більше за кількість CPU; інакше exit 2 до будь-якої роботи. Порожнє значення =
  не задано.
- Сумарна паралельність обмежена явно: `BOOKSWAP_JEST_WORKERS × BOOKSWAP_TEST_CONCURRENCY ≤ CPU`.
- Інтеграційні набори завжди мають рівно один воркер (з власних конфігів) і йдуть один за одним.
- Fast виконує пакети по черзі з тим самим `--maxWorkers`.
- Retries, збільшені таймаути чи виключення тестів для приховування перевантаження не використовуються.

**Значення за замовчуванням** обрано під поточний WSL (16 CPU, 10 ГБ RAM, 3 ГБ swap): 4 воркери — це той
самий ліміт, який Web уже мав після вимірювання (коментар у `apps/web/jest.config.js`: 15 воркерів — 409 с
і 45 падінь; 4 — 43 с, усе зелене).
Якщо пам'яті мало: `BOOKSWAP_JEST_WORKERS=2` — Standard повільніший (86 с проти 51 с), але пік пам'яті нижчий
(2,8 ГБ проти 3,9 ГБ; див. benchmark). lint + typecheck із типовим concurrency Turbo (10) мали пік ~3,6 ГБ,
тому для них тепер 2.

**CI.** Кожна з трьох job Full виконується на окремому runner'і, тож їхня пам'ять не сумується.
У блоці `env` workflow явно задано `BOOKSWAP_JEST_WORKERS=2`,
`BOOKSWAP_TEST_CONCURRENCY=1`, `BOOKSWAP_TURBO_CONCURRENCY=2`; це той самий профіль, з яким локальний
Full пройшов. Ліміти перевіряє `limits.mjs`; змінювати їх слід у цьому блоці.

## CI і обов'язкова перевірка перед merge

`.github/workflows/ci.yml` запускає Full на кожен `push`, `pull_request` і вручну через
`workflow_dispatch`, без path-фільтрів. Fast залишається локальним засобом розробки; Standard — перша
частина CI. Ручний запуск виконує той самий Full, що й автоматичні події:

| Job            | Частина Full                                    |
| -------------- | ----------------------------------------------- |
| `verify`       | format, lint, typecheck, `run.mjs suites unit --force`, build |
| `database`     | `run.mjs suites db-setup e2e db` (PostgreSQL — service) |
| `browser-e2e`  | встановлення Chromium, `run.mjs suites browser` |
| `full` — **«Full test suite»** | підсумок: `needs` усіх трьох, `if: always()`; зелений лише якщо **кожна** з них `success` |

`always()` навмисне: з умовою за замовчуванням провалена чи скасована job **пропустила** б підсумкову, а
пропущений required check GitHub зараховує як пройдений. `wiring.test.mjs` перевіряє, що CI запускає всі
кроки Full, а підсумкова job залежить від усіх інших.
Додаткові тести виконують справжній shell-крок підсумку для кожної job у станах `success`, `failure`,
`cancelled` і `skipped`, а також для порожнього набору результатів. Лише всі `success` дають exit 0.

Workflow використовує мінімальні `permissions: contents: read`. Новий прогін скасовує застарілий лише
для тієї самої події й гілки/PR; прогони різних гілок не заважають один одному.
Ліміти тривалості jobs: verify — 30 хв, database/browser — 45 хв, підсумок — 5 хв.
Jest test timeouts і retries не змінювалися.

Після публікації цієї конфігурації ручний запуск і перегляд:

```bash
gh workflow run ci.yml --ref codex/bs-152-three-tier-testing
gh run list --workflow ci.yml --branch codex/bs-152-three-tier-testing
gh run view <run-id> --log-failed
```

Статичну перевірку workflow виконано `actionlint 1.7.12` (офіційний release, SHA-256 перевірено).
Інструмент запускався одноразово з `/tmp`, залежності проєкту не змінені.

**Стан обов'язковості (перевірено 03.11.2026 через GitHub API):** окремий ruleset
[main_full_test_suite](https://github.com/DanOhurtsov/bookswap/rules/26453772), ID `26453772`, активний.
Для `refs/heads/main` він вимагає `Full test suite` саме від GitHub Actions (integration ID `15368`),
без bypass, з `strict_required_status_checks_policy: true`. Ефективні правила перевірено через
`GET /repos/DanOhurtsov/bookswap/rules/branches/main`.

Наявний `main_protect` лишається Disabled: його сторонні deployment-правила не вмикалися.
Нова workflow-job уже підготовлена локально, але ще не запускалася в GitHub: потрібні окремо
дозволені commit/push цієї гілки. До успішного check GitHub блокуватиме merge до `main`.

## Benchmark до виправлень рев'ю

**Середовище.** WSL2 (kernel 6.18), 16 CPU, `memory=10GB` у `.wslconfig` (9,7 ГБ видно), swap 3 ГБ, із якого
1,6–2,8 ГБ вже було зайнято до прогонів; паралельно працювали VS Code Server (~1,5 ГБ) і контейнер
PostgreSQL 17. Node 22.23.2, pnpm 11.21.0, Turbo 2.10.10, Jest 30. Дата — 03.11.2026.

**Метод вимірювання пам'яті.** Скрипт поза репозиторієм кожні 500 мс обходить **усе дерево процесів**
прогону (за `ppid`) і сумує RSS (`/proc/<pid>/status`) та PSS (`/proc/<pid>/smaps_rollup`); фіксується пік
кожної суми, мінімум `MemAvailable` системи й максимум зайнятого swap. Обмеження: сума RSS завищує спільні
сторінки (тому основне число — PSS); короткі піки між вибірками не видно; пам'ять PostgreSQL у Docker і
tmpfs (`/tmp`, де лежить кеш Jest) у дерево не входить — її відображає лише `MemAvailable`. Пік одного
процесу (`/usr/bin/time`) не використовувався.

## Рішення після рев'ю

- **Pre-commit:** погоджено версіонований хук без нової залежності; додано `pnpm hooks:install`,
  локально встановлено `core.hooksPath=.githooks`, перевірено виконання Standard та передачу його помилки.
- **Required check:** погоджено й створено окремий активний `main_full_test_suite`; ефективне правило
  для `main` перевірено через API.
- **Chromium:** установлено лише відсутні `libasound2t64` і `libasound2-data`; headless launch успішний.
- **Ізоляція:** погоджено перенесення міграцій та подвійного seed з dev-бази в захищену `_test`-базу.
  Небезпечний збіг із робочою базою перевірено окремим тестом до будь-якого підключення.
- **Ресурси:** CI quality tasks також отримують перевірений Turbo concurrency; для одного CPU типовий
  concurrency тепер 1. Некоректний незакритий JSONC-коментар завершує аналіз помилкою замість зависання Fast.
- **Порядок gate/build і Turbo DB-залежності:** лишено навмисно; зібрана API CLI потрібна DB-тестам,
  quality checks не вилучалися.
- **Залишилося:** перший віддалений CI-прогін цієї конфігурації після дозволених commit/push.
  Локальний Full і весь gate зелені, див. нижче.
